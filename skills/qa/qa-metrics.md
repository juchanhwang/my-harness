## 데이터 출처 규칙

수치는 데이터 출처(이슈 트래커, CI 기록 등)가 있을 때만 쓴다. 출처가 없으면 값을 지어내지 말고 "데이터 없음 — 필요한 출처: …"로 적는다.

이유: 에이전트에게 결함 데이터가 주어지지 않는 경우가 많고, 수치를 요구받으면 그럴듯한 숫자를 만들 위험이 있다.

예: `DER: 데이터 없음 — 필요한 출처: QA 단계 발견 버그와 프로덕션 발견 버그 목록(이슈 트래커)`

## 핵심 QA 메트릭

| § | 메트릭 | 계산식 | 목표·구간 | 필요한 출처 |
| --- | --- | --- | --- | --- |
| 1 | 결함 탈출률 (Defect Escape Rate, DER) | 프로덕션 버그 수 / (QA에서 발견된 버그 + 프로덕션 버그) × 100 | < 5% 우수 · 5-15% 양호 · 15-30% 개선 필요 · > 30% 심각 | 이슈 트래커 (발견 단계 구분) |
| 2 | 코드 커버리지 | 테스트로 실행된 코드 / 전체 코드 × 100 | 프로젝트 threshold (아래 참고), Branch 우선 | CI 커버리지 리포트 |
| | 요구사항 커버리지 | 테스트로 검증된 요구사항 / 전체 요구사항 × 100 | — | 요구사항(PRD) ↔ 테스트 매핑 |
| 3 | 테스트 실패율 | 실패한 테스트 / 전체 테스트 × 100 | CI 테스트 통과율 > 98% | CI 실행 기록 |
| | 플레이키 비율 | 불안정 테스트 / 전체 테스트 × 100 | < 2% | CI 실행 기록 |
| 4 | MTTR (버그 수정) | Σ(수정 완료 시각 − 신고 시각) / 총 버그 수 | Critical < 4시간 · Major < 2일 · Minor < 1주 · nit 스킵 가능(백로그) | 이슈 트래커 (신고·수정 시각) |
| 5 | 테스트 실행 시간 | — | 단위 < 2분 · 통합 < 5분 · E2E < 15분 · 전체 파이프라인 < 20분 | CI 실행 기록 |

- DER이 QA의 가장 중요한 성과 지표다. 버그 수가 아니라 DER로 QA를 평가한다.
- 코드 커버리지 기준값은 프로젝트 threshold가 원본이다 — FE는 `~/.claude/skills/fe/testing-vitest-setup.md`, BE는 `~/.claude/skills/be/testing.md`. 여기서는 수치를 정하지 않고 추이와 Branch 비중을 본다. 요구사항 커버리지가 코드 커버리지보다 비즈니스적으로 의미가 크다.
- MTTR이 둘이다. 4는 버그 티켓 수정 시간(이슈 트래커), 6-4는 장애 복구 시간(DORA)이다. 섞어 쓰지 않는다.

### 6. DORA Four Keys (배포/운영 메트릭)

> 출처: Forsgren, Humble, Kim, *Accelerate: The Science of Lean Software and DevOps* (IT Revolution, 2018) · [dora.dev/research/](https://dora.dev/research/) — 2023 State of DevOps Report 기준

결함 관점의 1~5와 달리 배포 신뢰성 관점이다. 함께 모니터링한다. Elite/High/Medium/Low 등급 구간표는 보고서 판마다 달라질 수 있어 싣지 않는다. 등급을 매길 때는 해당 연도 보고서의 표를 출처와 함께 쓴다.

| § | 메트릭 | 계산식 | QA 관점 |
| --- | --- | --- | --- |
| 6-1 | Deployment Frequency | 단위 기간 내 프로덕션 배포 횟수 | 낮으면 변경이 몰려 QA 부담이 급증한다. 자주 배포할수록 변경 범위가 작아 원인 추적이 쉽고 결함이 줄어든다 |
| 6-2 | Lead Time for Changes | 커밋 → 프로덕션 도달까지 걸린 시간 | 길면 테스트 병목일 가능성이 높다. 5(실행 시간)와 함께 보면 원인이 드러난다 |
| 6-3 | Change Failure Rate (CFR) | (장애·롤백·핫픽스로 이어진 배포 수 / 전체 배포 수) × 100 | 1(DER)의 배포 단위 버전이다. DER은 결함 단위, CFR은 배포 단위 실패율이다 |
| 6-4 | Mean Time to Restore (장애 복구 MTTR) | 프로덕션 장애 발생 → 서비스 정상화까지의 시간 | 아래 분해로 병목을 찾는다 |

총 다운타임 = MTTD(발생 → 감지) + MTTA(감지 → 담당자 인지) + MTTR(resolve, 인지 → 복구 완료). 세 지표를 모두 재야 병목이 드러난다 — MTTR(resolve)만 보면 알람이 안 와서 6시간 뒤 발견한 장애도 복구 시간이 짧게 기록된다. 개선 지점은 감지는 모니터링·알람 품질, 인지는 on-call 체계, 복구는 롤백 자동화·runbook·카나리 배포다.

## 에러 버짓

SLO를 QA 게이트로 쓴다. Error Budget = 100% − SLO (예: SLO 99.9% → 0.1%). 배포 승인 기준에 테스트 통과 여부뿐 아니라 "지난 30일간 에러 버짓이 얼마나 남았는가"를 넣는다. 잔량은 SLO와 모니터링 기록이 있을 때만 계산한다. QA는 SLI(가용성, p99 레이턴시, 에러율 등) 정의에 참여한다.

| 잔량 | 릴리스 운영 |
| --- | --- |
| 여유 있음 | 과감한 실험·릴리스 허용 |
| 절반 소진 | 릴리스 속도 감속, 회귀 테스트 강화 |
| 소진 임박 | 새 기능 릴리스 중단, 안정성 개선에만 집중 |
| 초과 | 롤백 + 포스트모템 + 근본 원인 제거 |

## 보조 메트릭

| 메트릭 | 계산식 | 목표·구간 | 필요한 출처 |
| --- | --- | --- | --- |
| 버그 밀도 | 발견된 버그 수 / KLOC | 좋음 < 2/KLOC · 보통 2-5 · 나쁨 > 5 | 이슈 트래커, 코드 규모 |
| 재오픈율 | 재오픈된 버그 / 수정된 버그 × 100 | < 10% (높으면 수정 품질 문제 또는 불명확한 버그 리포트) | 이슈 트래커 |
| 자동화율 | 자동화된 테스트 케이스 / 전체 테스트 케이스 × 100 | > 70% (회귀 테스트 기준) | 테스트 케이스 목록 |
| 결함 제거 효율 (DRE) | 릴리스 전 발견 결함 / 전체 결함 × 100 (같은 결함 집합이면 100% − DER) | > 95% (Capers Jones, *Software Engineering Best Practices*, 2010 — 엘리트 팀 기준) | 이슈 트래커 |

## 메트릭 활용

- 트렌드가 숫자보다 중요하다. DER은 한 시점의 값보다 연속 감소 여부가, 커버리지는 한 시점의 값보다 스프린트마다 늘고 있는지가 더 의미 있다.
- 메트릭 자체가 목표가 되면 왜곡된다(Goodhart's Law). 하지 않는 것:
  - 커버리지 100% 강제 → 프로젝트 threshold + Branch 중심으로 본다
  - 버그 수로 QA 평가 → DER로 평가한다 (많이 찾는 것보다 예방이 중요하다)
  - 메트릭 조작(테스트 건너뛰기, 분류 조작) → 자동 수집·투명성으로 막는다
  - 개인 단위 메트릭 → 팀·시스템 메트릭으로 본다

## 스프린트 QA 리포트 템플릿

수치 칸에는 「데이터 출처 규칙」을 적용한다. 출처가 없는 칸은 값을 비우고 "데이터 없음 — 필요한 출처: …"로 적는다.

```markdown
# Sprint XX QA Report

## 요약
- 테스트 케이스: N개 실행, N개 통과 (X%)
- 발견 버그: N개 (Critical: N, Major: N, Minor: N, nit: N)
- 수정된 버그: N개
- DER: X%

## 핵심 지표
| 메트릭 | 이번 | 지난 | 변화 |
|--------|------|------|------|
| DER | X% | X% | ↓ |
| Coverage | X% | X% | ↑ |
| Pass Rate | X% | X% | → |
| MTTR (Critical) | Xh | Xh | ↓ |

## 주요 이슈
1. [Major] 이슈 설명 — 상태, 담당자

## 개선 제안
1. 제안 내용

## 다음 스프린트 QA 계획
1. 계획 내용
```

## 메트릭 체크리스트

- [ ] 핵심 메트릭 4가지(DER, Coverage, Pass Rate, MTTR)를 추적한다
- [ ] 모든 수치에 데이터 출처가 있다 (없으면 "데이터 없음 — 필요한 출처: …")
- [ ] 스프린트마다 QA 리포트를 쓰고, 트렌드에서 개선 액션을 도출한다
- [ ] 개인이 아닌 팀·시스템 수준의 메트릭이다
