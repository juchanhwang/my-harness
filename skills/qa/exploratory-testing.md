# 탐색적 테스트 (Exploratory Testing)

> 참조: [Michael Bolton — FEW HICCUPPS](https://developsense.com/blog/2012/07/few-hiccupps) · [James Bach — Heuristic Test Strategy Model](https://www.satisfice.com/download/heuristic-test-strategy-model)

스크립트 없이 경험으로 시스템을 탐험해 자동화가 놓치는 **예상하지 못한 문제**를 찾는다. 차터(목표)·타임박스(30~90분)·세션 노트가 없으면 즉흥(ad-hoc) 테스트다. 재현과 학습이 남지 않는다.

## 세션 형식

**차터** — 세션 시작 전에 쓴다.

```markdown
**탐색 대상**: 결제 프로세스 (카드 결제) | **시간**: 45분
**목적**: 결제 실패 시 사용자 경험 검증
**탐색 아이디어**: 유효하지 않은·만료된 카드 / 결제 중 네트워크 끊기·뒤로가기·새로고침 / 1원·매우 큰 금액 / 더블 클릭·다른 탭에서 동시 결제
```

**노트** — 세션 중에 쓴다.

```markdown
**차터**: 결제 프로세스 탐색 | **시간**: 14:00-14:45 (45분) | **테스터**: <이름> | **빌드**: v2.3.1-rc1
**버그**
1. [Major] 결제 버튼 더블 클릭 시 두 번 결제됨 — 디바운스 없음
2. [Minor] 만료된 카드 에러 메시지가 영어로 표시 ("Card expired")
**질문**: 결제 실패 후 재시도 제한이 있어야 하지 않나?
**아이디어**: 결제 완료까지 버튼 비활성화
```

**리포트** — 여러 세션을 모아 전달한다.

```markdown
**기간**: <시작일> ~ <종료일> | **테스터**: <이름> | **빌드**: v2.3.1-rc1 | **총 세션**: 4개 (180분)

| 세션 | 차터 | 시간 | 버그 | 질문 |
|---|---|---|---|---|
| 1 | 결제 프로세스 | 45분 | 2 | 2 |
| … | … | … | … | … |

**발견 요약**: 버그 8개 (Critical: 0, Major: 1, Minor: 5, nit: 2) · 질문 4개 · 아이디어 6개
**가장 리스크 높은 영역**: 1. 결제 — 더블 클릭 방지 없음 2. 검색 — XSS 가능성 있는 입력 처리
```

## 휴리스틱

**SFDPOT — 제품 요소(Product Elements, James Bach)**: 무엇을 탐색할지 정하는 질문이다.

| 약자 | 탐색 질문 |
|---|---|
| **S**tructure | 어떤 모듈이 가장 복잡한가? |
| **F**unction | 이 기능이 모든 조건에서 동작하는가? |
| **D**ata | 빈 값(null·빈 배열/객체), 경계값(0·-1·최대), 대용량, 특수문자는? |
| **P**latform | 브라우저·OS·디바이스 차이, 네트워크 장애·느린 네트워크·타임아웃은? |
| **O**perations | 장시간 사용, 업데이트, 백업은? |
| **T**ime | 동시성(더블 클릭·동시 요청), 타임존, 만료, 자정은? |

엣지 케이스(null·빈 배열/객체, 경계값, 동시성, 네트워크 장애/타임아웃)는 Data·Platform·Time 행에서 시작한다. 케이스 설계 기법(경계값 분석 등)은 `test-design.md`를 따른다.

**FEW HICCUPPS — 일관성 휴리스틱 (Michael Bolton)**: 제품이 무엇과 어긋나는지로 문제를 알아본다.

| 약자 | 탐색 질문 |
|---|---|
| **F**amiliarity | 전에 본 버그 유형이 여기서도 나타나는가? |
| **E**xplainability | 이 동작을 사용자에게 설명할 수 있나? |
| **W**orld | 현실 세계의 상식과 맞나? |
| **H**istory | 이전 버전과 일관되나? |
| **I**mage | 조직이 보여주려는 이미지·브랜드에 맞나? |
| **C**omparable products | 같은 제품군·경쟁 제품은 이걸 어떻게 처리하나? |
| **C**laims | 명세·문서·사람들이 말한 대로 동작하나? |
| **U**sers' desires | 합리적인 사용자가 원하는 동작인가? |
| **P**roduct | 같은 제품 안의 비슷한 요소끼리 일관되나? |
| **P**urpose | 명시적·암묵적 사용 목적을 달성하나? |
| **S**tatutes and standards | 관련 법규와 접근성·보안·업계 표준에 맞나? |

## 탐색 기법

- **투어**: 가이드(매뉴얼대로만) · 무법자(허용되지 않은 모든 것 시도) · 쓰레기 수집가(가장 안 쓰는 기능) · 랜드마크(핵심 기능만 빠르게 순회) · 슈퍼 모델(UI만: 레이아웃·일관성) · 역사가(이전 버전과 비교)
- **페르소나**: IT 비전문가(60대, 첫 사용) · 바쁜 사용자(빠르게 클릭, 기다리지 않음) · 악의적 사용자 · 국제 사용자(한국어 외 환경) · 장애인 사용자(키보드만, 스크린리더) · 모바일 사용자(느린 네트워크, 작은 화면)
- **시나리오 변형**: 해피 패스(로그인 → 상품 선택 → 장바구니 → 결제)에서 한 곳씩 바꾼다. [뒤로가기] 후 다른 상품 / [브라우저 닫기·재접속] 후 장바구니 유지? / 상품 100개 / [로그인 안 함] 상태로 결제 시도 → 로그인 유도?

## 체크리스트

- [ ] 탐색 세션에 명확한 차터가 있는가
- [ ] 타임박싱(30-90분)이 되어 있는가
- [ ] 세션 노트를 기록하고 있는가
- [ ] 다양한 휴리스틱을 활용하고 있는가
- [ ] 발견 사항이 분류되는가 (버그/질문/아이디어, 버그는 Critical/Major/Minor/nit)
