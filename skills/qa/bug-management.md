# Bug Management

## 버그 리포트

개발자가 리포트만 보고 재현할 수 있어야 한다. 제목은 `[영역] 간결한 증상` 형식이다 (예: `[상품관리] 정수 가격 입력 시 500 에러 발생`). "버그 발견", "에러남"처럼 증상이 없는 제목은 쓰지 않는다.

```markdown
## 제목
[영역] 간결한 증상

## 환경
- OS / 브라우저 / 디바이스(해상도) / 앱 버전 / 계정 유형

## 재현 단계
1. <URL, 계정, 입력값까지 구체적으로>

## 기대 결과

## 실제 결과
<에러 메시지, 콘솔·네트워크 로그 (예: POST /api/products 500)>

## 재현율
N/M (항상 재현이면 10/10)

## 스크린샷/영상

## 추가 정보
<발생 조건을 좁히는 단서 (예: 소수점 가격은 정상, 정수만 실패)>
```

## Severity vs Priority

|              | 정의           | 누가 결정? |
| ------------ | ------------ | ------ |
| **Severity** | 기술적 영향도      | QA     |
| **Priority** | 비즈니스 수정 우선순위 | PM/PO  |

둘은 독립이다. 어드민 전용 기능의 크래시는 Severity 높음·Priority 낮음, 랜딩 페이지 오타는 Severity 낮음·Priority 높음(브랜드 이미지에 즉시 영향)일 수 있다.

### Severity 분류

qa-check 역할과 같은 네 단계를 쓴다. 리드 모드 트리아지와 역할 리포트가 다른 체계를 쓰면 같은 결함이 두 등급을 갖게 된다. 판정이 애매하면 역할 문서의 기준표가 원본이다 — 코드는 `~/.claude/skills/qa-check/references/review.md`의 표, 인수 조건은 같은 폴더 `acceptance.md` 7항, 시안 대비 스타일은 `~/.claude/skills/qa/figma-style-audit.md` §5.

| Severity | 기준 | 예시 |
| --- | --- | --- |
| **Critical** | 기능을 쓸 수 없음, 데이터 손상·유실, 보안 취약점 | 결제 불가, 저장한 데이터 유실, XSS |
| **Major** | 핵심 흐름 일부 실패, 요구사항(PRD)과 다른 동작, 누적되는 리소스 누수, 시안 대비 색·타이포 불일치 | 검색 결과 잘못, 이메일 발송 실패, 버튼 색이 시안과 다름 |
| **Minor** | 영향이 작은 엣지 케이스·표시 문제, 시안 대비 간격·radius 불일치, 테스트 누락 | 잘못된 날짜 포맷, 화면 문구 오타, padding 4px 차이 |
| **nit** | 동작·표시에 영향 없는 명명·형식 (스킵 가능, 리포트에는 적는다) | 변수명, 코드 포맷 |

### Priority 분류

| Priority        | 설명        | SLA    |
| --------------- | --------- | ------ |
| **P1 — Urgent** | 즉시 수정     | 4시간 이내 |
| **P2 — High**   | 현 스프린트 수정 | 2일 이내  |
| **P3 — Medium** | 다음 스프린트   | 2주 이내  |
| **P4 — Low**    | 백로그       | 일정 미정  |

### Severity-Priority 매트릭스

```
        Priority
               P1   P2   P3   P4
Critical │  🔴   🔴   -    -
Major    │  🔴   🟡   🟡   -
Minor    │  🟡   🟢   🟢   🟢
nit      │  -    🟢   🟢   ⚪

🔴 즉시/현 스프린트  🟡 빠른 시일  🟢 계획적  ⚪ 백로그
```

## 트리아지

순서: 재현 확인 → Severity 판정 → 중복 확인 → Priority·담당자 결정 → 상태 추적. 재현이 안 되면 추가 정보를 요청하거나 닫고(아래 「재현이 안 되는 버그」), 중복이면 기존 이슈에 링크하고 닫는다.

- 상태는 Open → In Progress → Fixed → Verified → Closed 순이다. QA 검증(verification)에 실패하면 Reopened로 되돌리고, Verified 없이 Closed 하지 않는다.
- 30일 넘게 Open인 버그와 중복 버그를 정기적으로 재검토한다.

## 재현이 안 되는 버그

다음 순서로 좁힌다: 환경 차이(OS, 브라우저, 해상도, 계정 권한) → 데이터 상태(특정 데이터에서만 발생하는가) → 타이밍(특정 시간대, 동시 접속, 네트워크 상태) → 로그(서버 로그, 브라우저 콘솔, 네트워크 탭) → 반복 시도(10회, 50회, 100회).

간헐적 버그는 재현율을 N/M(%)로 적고 의심 원인과 추가 조사 항목을 남긴다.

```markdown
## 재현율: 3/20 (15%)

## 의심 원인
- <예: Race condition — 두 API 호출이 동시에 완료될 때 / 네트워크 지연 — 응답이 3초 이상>

## 추가 조사 필요
- [ ] <예: 서버 로그의 동시 요청 패턴 / 네트워크 스로틀링 재현 / 동시성 처리 코드 리뷰>
```

## 버그 메트릭

MTTR(버그 수정), 재오픈율, 버그 밀도의 정의와 목표는 `qa-metrics.md`를 따른다. 이 문서에만 두는 지표는 버그 발견율(스프린트당 발견 버그 수, 추세 감소)과 버그 수정율(수정된 / 발견된, > 90%)이다.
