# Regression Strategy

## 범위 결정

전체 회귀(신뢰도 높지만 오래 걸림)는 메이저 릴리스에, 선택적 회귀(빠르지만 놓칠 수 있음)는 일반 스프린트에 쓴다. 리스크 기반 선택을 항상 기본으로 권장한다(기준은 `test-strategy.md` 「리스크 기반 우선순위」). 선택적 회귀는 변경 영역에서 바깥으로 넓히고, 핵심 비즈니스 플로우는 변경과 무관하게 항상 포함한다.

| 우선순위 | 대상 | 예 (결제 모듈 변경) |
| --- | --- | --- |
| 1 필수 | 변경 영역 + 항상 포함 | 결제 모듈 + 로그인, 핵심 결제 플로우, 데이터 무결성 |
| 2 높음 | 직접 영향 | 장바구니, 주문 내역, 환불 |
| 3 시간 여유 시 | 간접 영향 | 이메일 알림, 대시보드 통계 |

## 스위트 구성

태그는 누적한다 — smoke 테스트는 critical·regression에도, critical 테스트는 regression에도 속한다. 핵심 결제 플로우는 `@smoke` `@critical` `@regression`을 모두 달고, 영역 태그(`@admin` 등)는 따로 단다.

| 층 | 규모 | 시간 | 내용 |
| --- | --- | --- | --- |
| Smoke | 5-10개 | < 5분 | 로그인, 핵심 페이지 로드, 핵심 API 응답 |
| Critical Path | 20-30개 | < 15분 | 가입 → 로그인 → 핵심 기능 → 결제 |
| Full Regression | 100+개 | < 60분 | 모든 기능의 주요 시나리오 |
| Extended | 200+개 | 야간 실행 | 엣지 케이스, 비기능, 크로스 브라우저 |

| 이벤트 | 실행 범위 |
| --- | --- |
| 커밋/PR | Unit + Integration (자동) |
| PR 머지 (main) | Smoke + Critical Path |
| 일일 (야간) | Full Regression |
| 릴리스 후보 | Extended + 탐색적 |
| 핫픽스 | Smoke + 관련 영역 |

## 테스트 부채

경고 신호:
- CI 전체 실행 시간 > 30분
- 플레이키 테스트 > 5% (목표는 `qa-metrics.md`의 < 2%)
- 스킵된 테스트 > 10개
- 마지막 테스트 정리 > 3개월 전
- "이 테스트가 뭘 하는지 모르겠다"는 반응

정리 순서: 플레이키 상위 5개 분석·수정(절차는 `e2e-testing.md` 「대기와 플레이키 방지」, 재현 불가 테스트는 제거하거나 재작성) → 중복·제거된 기능·스킵 상태 테스트 정리 → 약한 assert 보강과 하드코딩 대기(`waitForTimeout`) 제거 → 느린 상위 10개와 불필요한 setup/teardown 최적화.

## 삭제 기준

| 삭제한다 | 삭제하지 않는다 |
| --- | --- |
| 제거된 기능의 테스트 | 과거 프로덕션 버그의 재발 방지 테스트 |
| 3개월 이상 skip 상태인 테스트 (삭제 또는 수정) | 핵심 비즈니스 로직 테스트 (결제, 인증, 데이터 무결성) |
| 같은 로직을 다른 방식으로 두 번 검증하는 중복 | 보안 테스트 (XSS, injection, 인가) |
| 가치 없는 테스트 (`expect(true).toBe(true)` 수준) | 규제 요구사항 테스트 |
| 구현 세부사항 테스트 (리팩토링마다 깨짐) | |

삭제는 PR로 하고 이유를 커밋 메시지에 적는다. 삭제 전후로 커버리지가 하락하지 않았는지 확인한다.

## 자동화 우선순위

중요하고 자동화하기 쉬운 것이 1순위, 덜 중요하지만 쉬운 것이 2순위, 중요하지만 어려운 것은 3순위(도구 개선 후), 덜 중요하고 어려운 것은 수동으로 유지한다.

자동화하지 않는 테스트: 한 번만 실행하는 것, UI가 매우 자주 변하는 영역, 주관적 판단이 필요한 것(UX·디자인 감성), 자동화 비용이 수동 비용보다 큰 것.

## 회귀 테스트 리포트

```markdown
## 회귀 테스트 결과 — <버전> 릴리스 후보

**실행 일시**: <일시> (<야간 등>)
**환경**: <Staging 등>
**총 테스트**: N개
**결과**: N Pass / N Fail / N Skip

### 실패 테스트
| # | 테스트 | 상태 | 담당자 | 분석 |
|---|--------|------|--------|------|
| 1 | <이름> | Fail | <담당자> | 새 API 호환 이슈 → <Critical/Major/Minor/nit> 생성 |
| 2 | <이름> | Fail | <담당자> | 플레이키(타이밍) → 수정 중 |

### 스킵된 테스트
| # | 테스트 | 이유 |
|---|--------|------|
| 1 | <이름> | <PG 샌드박스 점검 중 등> |

### 릴리스 판단
<조건부 승인 등> — <재테스트가 필요한 영역>
```

## 장애 후 재발 방지 기록

장애가 나면 회귀 suite가 왜 못 잡았는지를 먼저 적는다. 원인보다 "테스트 공백"이 이 기록의 목적이다.

```markdown
## 장애 기록 — <날짜> <요약>
- 영향: <무엇이 얼마나 멈췄나>
- 근본 원인: <코드·설정·환경>
- 왜 테스트에서 못 잡았나: <CI와 운영의 차이, 조용한 실패(에러 대신 기본값) 등>
- 재현 테스트: <추가한 테스트 위치> — 회귀 suite 편입 여부
- 개선 액션: [완료]/[진행]/[계획] <항목>
```
